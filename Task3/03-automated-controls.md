# 3. Автоматизированный контроль

Цель контроля — чтобы отклонение от стратегии (незашифрованный том, открытый порт, просроченный
сертификат, ПДн в неположенном месте) обнаруживалось и блокировалось автоматически, а не на ежегодном
аудите. Контроли встроены в три точки: **до развёртывания** (CI/CD), **при развёртывании** (admission в
Kubernetes) и **в эксплуатации** (сканирование, мониторинг, SIEM).

## 3.1. Превентивный контроль: политики как код

| Контроль | Правило | Инструмент | Реакция |
|---|---|---|---|
| Шифрование томов | `PersistentVolumeClaim` только с `StorageClass` из списка зашифрованных; `hostPath` запрещён | Kyverno / OPA Gatekeeper | admission deny |
| TLS на входе | `Ingress`/`Gateway` без TLS-секрета или с TLS < 1.2 запрещён; HSTS обязателен | Kyverno, конфигурация Ingress-контроллера | admission deny |
| mTLS внутри | `PeerAuthentication` только `STRICT`; namespace без mesh-инъекции не допускается в контур ИСПДн | Istio/Linkerd policy + Kyverno | admission deny |
| Подключения к БД и брокерам | `sslmode=verify-full` в ConfigMap/Secret обязателен; `PLAINTEXT` listener Kafka запрещён | Kyverno (проверка аннотаций), Kafka operator | admission deny / CI fail |
| Секреты | секреты только через Vault CSI/Agent; `Secret` в git и образах запрещены | gitleaks, trufflehog в CI; Kyverno | CI fail, блокировка merge |
| Инфраструктура как код | Terraform/Helm проверяются на шифрование (S3 SSE, EBS/PV encryption, TLS) и публичные бакеты | checkov, tfsec, Polaris | CI fail |
| Образы | уязвимости критического уровня и устаревшие TLS-библиотеки | Trivy / Grype в CI и в registry | CI fail, карантин образа |
| API-контракты | все `servers` в OpenAPI — `https`; поля с тегом `pii.*` не отдаются внешним клиентам без `x-anonymized`/consent-scope | Spectral с кастомными правилами, контрактные тесты (Privacy Gate из Task 2) | CI fail |
| Схемы данных | новая колонка без тега; колонка `pii.id/contact` без атрибута `protection=encrypt-column` | линтер миграций (Liquibase/Flyway hook), проверка по каталогу | CI fail |

## 3.2. Детективный контроль: сканирование и верификация

| Контроль | Что проверяет | Инструмент | Частота | Реакция |
|---|---|---|---|---|
| Конфигурация TLS внешних и внутренних эндпоинтов | версии протокола, наборы шифров, цепочка, HSTS, OCSP | testssl.sh / sslyze по инвентарю эндпоинтов из каталога | еженедельно + после релиза | тикет Security, при TLS 1.0/1.1 — алерт |
| Срок действия сертификатов | все сертификаты (Ingress, mesh, БД, партнёрские, КЭП) | cert-manager метрики, x509-certificate-exporter → Victoria Metrics | непрерывно | алерт за 14 дней, критический за 3 дня |
| Ротация ключей | факт и успешность ротации по расписанию Vault | Vault audit log + метрики, Airflow-джоб проверки | ежедневно | алерт при пропуске ротации |
| Использование ключей | аномалии: всплеск `decrypt`, обращение к ключу домена из чужого namespace, операции вне рабочего времени | Vault audit → OpenSearch, SIEM/UEBA-правила | непрерывно | алерт Security, временная блокировка политики |
| Шифрование томов и дисков фактически | состояние LUKS на узлах, `encrypted=true` у PV, BitLocker на рабочих станциях | node-exporter textfile / osquery, MDM-отчёты | ежедневно | алерт, карантин узла/станции (NAC) |
| Соединения с БД | доля сессий без SSL (`pg_stat_ssl`), подключения с паролем вместо сертификата | postgres-exporter, pgaudit | непрерывно | алерт, при > 0 — блокировка пользователя |
| Kafka | клиенты без TLS/SASL, топики с тегом `pii.med` без ACL или с retention > 7 дней | Kafka admin API, скрипт проверки по каталогу | ежедневно | алерт |
| Обнаружение ПДн вне положенных мест | ПДн в логах, в бакетах аналитики без `anonymized=true`, в теме письма, в ноутбуках Jupyter | OpenMetadata profiler + Presidio, OpenSearch ingest regex, DLP, скан `.ipynb` при сохранении | ежедневно / при событии | инцидент владельцу данных, автоматическая маскировка логов |
| Качество обезличивания | k-анонимность ≥ 5 и l-разнообразие в curated-наборах; попытка выгрузки квази-идентификаторов | тест в конвейере (dbt test / Great Expectations), правила шлюза доступа | при каждой сборке набора | набор не публикуется, тег `anonymized` не ставится |
| Резервные копии | бэкап зашифрован, целостность, тестовое восстановление в изолированный namespace, object lock активен | pgBackRest verify, Velero hooks, Airflow restore-test | ежедневно (verify), еженедельно (restore) | алерт, инцидент при неудачном восстановлении |
| Сеть | открытые протоколы (HTTP, FTP, Telnet, LDAP без TLS, SMB1), неожиданные потоки из контура ИСПДн, статус VPN-туннелей | Suricata/Zeek на зеркале трафика, NetFlow, мониторинг криптошлюзов | непрерывно | алерт, блокировка на МЭ |
| Почта | TLS на коннекторах, вложения с меткой R, DLP-срабатывания | Exchange отчёты, DLP | непрерывно | блокировка письма, уведомление офицера безопасности |
| Соответствие бенчмаркам | CIS Kubernetes, CIS PostgreSQL, ФСТЭК 21 (чек-лист) | kube-bench, pgaudit + скрипты, Wazuh SCA | еженедельно | отчёт и тикеты |
| Целостность критичных файлов и конфигураций | изменения конфигов TLS, политик, образов | Wazuh FIM, подпись образов (cosign) и проверка при admission | непрерывно | алерт, откат |

## 3.3. Мониторинг и метрики

Метрики шифрования публикуются в Victoria Metrics и выводятся на дашборд «Приватность и криптография»
(доступ: CTO, офицер безопасности):

| Метрика | Целевое значение | Алерт |
|---|---|---|
| Доля PV и дисков с подтверждённым шифрованием | 100 % | < 100 % |
| Доля внешних эндпоинтов с оценкой TLS «A» (testssl) | 100 % | любой ниже «A» |
| Доля внутренних соединений под mTLS (mesh telemetry) | 100 % | < 99 % |
| Сертификаты, истекающие < 14 дней | 0 | ≥ 1 |
| Просроченные ротации ключей | 0 | ≥ 1 |
| Аномальные операции с ключами за сутки | 0 | ≥ 1 |
| Находки ПДн вне разрешённых хранилищ | 0 | ≥ 1 |
| Успешность тестового восстановления бэкапов | 100 % | неудача |
| Доля сессий PostgreSQL без SSL | 0 % | > 0 % |
| DLP-блокировки вложений класса R | тренд | всплеск |

Все алерты идут в Alertmanager → дежурная смена и SIEM; инциденты с утечкой запускают процедуру
уведомления РКН (24 ч первичное, 72 ч итоговое) по плану реагирования из `Task1/05-controls.md` (C-17).

## 3.4. Периодические проверки с участием людей

| Проверка | Периодичность | Кто |
|---|---|---|
| Пересмотр модели угроз и класса СКЗИ, актуализация реестра средств | раз в год и при изменении архитектуры | CTO, офицер безопасности |
| Key ceremony: проверка резервных копий ключей HSM, смена долей Shamir | раз в год и при смене владельцев долей | офицер безопасности, CTO |
| Пентест внешнего периметра и API, включая проверку BOLA и downgrade TLS | раз в год и перед крупным релизом | внешний подрядчик |
| Учения по восстановлению из бэкапа после «шифровальщика» | раз в полгода | администратор, CTO |
| Аудит прав доступа и ключей, отзыв неиспользуемых | ежеквартально | офицер безопасности, владельцы доменов |
